# Plan: make the self-hosting, exactness and isolation claims literally true

**Status:** started 2026-11-04 from `main` at `47ea545`. Phases 0 and 1 are merged (#22) and passed CI. Phase 2 passes every gate locally, but has not yet run in CI. Phases 3 and 4 have not started.

**Direction:** close documentation gaps by making the code more capable, and remove dependencies on other languages wherever possible. FrancOS's own runtime is the implementation that matters. Correct behaviour is defined by a language-neutral data table, not by another implementation.

## Evidence that shaped this plan

Measured on `main` in disposable containers with QEMU 7.2 and binutils 2.40.

| Finding | Consequence |
|---|---|
| A kernel built by `stage4/compiler.py` (177,720 bytes) rebuilt the OS and produced `compiler/bootstrap_seed.S` byte for byte | An independent seed check is already possible |
| `1099511627776/3 847288609443/1099511627776 *` gives `NaN` natively; the true result `282429536481` fits | "Exact when the result fits" is false in the native runtime |
| `1/0 1 +`, `1/0 1 -`, `1/0 2 *`, `1/0 1/0 *` give `NaN` natively; the documented value is infinity | Exceptional values differ from the documented table |
| `1 1/0 /` gives `NaN` natively; the documented formulas give `0` | Same |
| `-7 3 %` gives `-1` natively and `2` hosted; native `%` ignores denominators | `%` needs a defined rule |
| `-9223372036854775808 % -1` resets the machine: `idivq` faults on that one case | Found by the conformance table |
| `def r r ;` then `r` resets the machine | One REPL line can take down the OS |
| Four `drop`s on an empty stack wedge the guest in an `S` flood | `fr_drop` has no underflow check |
| The kernel stack starts at `0x80000`, inside `.bss`, with Ring 3 stack, code and page tables 4 KiB below it | Likely cause of the recursion reset; not yet proven |
| The IDT is only installed by `irq-start` | At boot, any CPU fault resets the machine |
| `kernel.bin` is 176,842 of 195,584 bytes | A toolchain cannot live in the kernel image |
| New variables must be declared in the seed; the runtime dictionary holds 512 entries | Both block a large Franc program |
| ATA writes reach only LBA 128-199; reads stop at LBA 4096 | Blocks writing a kernel image on device |

## Order

Phase 0, then 1, 2 and 3, then the Phase 4 capstone. Phases 0-2 avoid a seed re-pin where possible, because `runtime/abi.S` is not a seed input. The one planned exception is step 7 of Phase 2.

## Phase 0: independent seed check

Build the kernel with `stage4/compiler.py`, run the native bootstrap from it, and compare generations 2 and 3 with the pinned seed.

- **Failure test:** an altered seed must fail the check.
- **Done when:** the check runs in CI on every change that can affect the seed.
- **Limit:** both paths share the runtime, binutils and author. This guards against a tampered seed, not against bugs in shared code.
- **Dependency note:** `compiler.py` is Python, but only verification uses it. No build or runtime path does. A diverse-compiler check needs a second compiler by definition, so it stays until a non-Python alternative exists.

## Phase 1: arithmetic conformance

`tests/arith/vectors.txt` is the rule: one expression and its expected result per line. Both the native runtime and, while it exists, hosted `frac.c` must match it. The runner is POSIX shell, and the check runs inside FrancOS.

Rules the table encodes:

- Finite results are exact whenever the reduced result fits a signed 64-bit numerator and denominator; otherwise they are bottom.
- Exceptional values follow the documented pair formulas, evaluated exactly.
- `%` takes two integers and returns a result with the sign of the divisor. A zero divisor or a non-integer operand gives bottom.
- Hosted one-operand percent, where `%` changes meaning with stack depth, is not part of the language rule and is not added to native.

Implementation in `runtime/abi.S`: keep the existing 64-bit path for values it already handles, so behaviour and speed there do not change. On overflow or an exceptional operand, use a 128-bit exact path with its working state on the machine stack, because preemptive tasks share these routines.

- **Downstream check:** `s2-patch` passes negative numbers through `%`. The self-host proof and JIT suites must confirm generated bytes do not change.
- **Done when:** every vector passes natively and hosted, and all suites still pass.

## Phase 2: crash safety

1. Reproduce the `S` flood and confirm or reject the recursion theory before changing anything.
2. Add floor and ceiling checks to all data-stack operations, sharing the check `fr_pop` already has.
3. Move the kernel stack above 1 MiB with a guard page. Extending it in place would reach VGA memory at `0xA0000`. Update `franctxt/memory.franctxt` and the UEFI loader's reservations.
4. Install the IDT and TSS at boot, with a separate double-fault stack.
5. Have `fr_s2_run` save a recovery point, so a fault prints an error and returns to the prompt.
6. Stretch: map kernel code read-only, so writes to it fault.
7. Boot only reads the disk. Write tests run from the `s` diagnostic, and only on a disk with the FrancOS signature. This step also shows runtime errors on the BIOS screen. `kernel/main.frac` is a seed input, so this is its own step with a seed re-pin.

- **Tests:** recursion, underflow and wild writes become regression tests. Valid deep recursion and the Ring 3 and preemption suites must keep working.
- **Done when:** those inputs cannot take down the OS, under both BIOS and UEFI.
- **Limit:** kernel-privilege code can still corrupt memory. Only general Ring 3 removes that.

## Phase 3: real self-hosting

Goal: FrancOS builds a complete bootable image with no host assembler or linker.

1. **Speed test first.** Build a minimal assembler for the instruction forms in the seed and time it on the 907 KB seed in QEMU. If it is far too slow, stop and rethink.
2. **Foundations (first seed re-pin).** Runtime variable allocation, higher dictionary limits, explicit disk write regions, wider disk reads, second-drive support, and compiler output to memory instead of serial.
3. **Toolchain bundle.** Load from its own disk area; the 141 KB of assembly source exceeds the 131,071-byte bundle limit.
4. **Full assembler.** About 130 mnemonics, 3 macros, `.include`, `.incbin`, `.ifc`, and 16/32-bit code. Every object is compared byte for byte with GNU `as`.
5. **Built-in linker.** Output a flat binary directly, compared with `ld` plus `objcopy`.
6. **Image writer.** A Home action builds a complete bootable image on a second disk, with sources stored on the image itself. The running disk is never modified.
7. **Final proof.** CI blocks `as`, `ld` and `objcopy` during the rebuild. The OS builds generation N and boots it; N+1 must match N and the binutils build. This includes the boot sector.

**Risks:** GNU `as` jump-size selection must be matched for byte-exact output. `ld` chooses the placement of 661 common symbols; if that cannot be matched, emit them in a fixed order, at the cost of a seed re-pin. New language primitives must also be added to `compiler.py`, or Phase 0 fails.

**Still true afterwards:** the very first seed needs GNU `as` once.

## Phase 4 (capstone): one OS, in the emulator and on a real laptop

**Goal:** FrancOS runs as fully as possible on a modern x86-64 Windows-class laptop, and behaves the same there as in the emulator. This comes after Phases 0-3.

**Generalizable by design:** one laptop is the first target, not the design boundary. FrancOS is an open-source project, so other people must be able to bring up their machines without changing the core.

- **Write to standards, not models.** Target UEFI, ACPI, GOP, NVMe, AHCI, xHCI and USB HID. A driver for a standard covers most PCs.
- **Discover, never assume.** Find devices by PCI class, memory from the firmware map, and display modes from GOP. No model names, fixed device addresses or laptop-specific constants in core code.
- **Stable driver interfaces.** Block, input, display, network and timer interfaces sit between drivers and the OS. Filesystems, the UI and apps never call a specific driver. Existing ATA, PS/2, VGA and e1000 code moves behind them, so legacy machines keep working.
- **Missing hardware is normal.** Every device is optional where the OS can run without it. Absence gives a clear message, not a hang or crash.
- **Quirks are data.** Unavoidable per-device workarounds live in one reviewed table keyed by device ID, not in driver logic.
- **Report what was found.** A built-in hardware screen lists detected devices, the driver bound to each, and what is unsupported. Contributors can paste it into a bug report.
- **Test a matrix, not one machine.** CI boots several QEMU profiles: machine types, firmware, storage, RAM sizes, screen resolutions, and devices absent.
- **Document it.** A driver guide, a hardware support list recording tested machines and results, and a template for submitting a new machine.

**Design rule:** change the emulator to match the laptop, not the reverse. A new QEMU profile uses UEFI, NVMe and xHCI USB, with no IDE, PS/2 or e1000. That profile becomes the primary test target, so the laptop drivers run in CI on every change. Laptop-only differences should be limited to what QEMU cannot model.

0. **Interfaces first.** Define the driver interfaces and move the existing ATA, PS/2, VGA and e1000 code behind them, with all current suites still passing. This comes before any new driver.
1. **Baseline.** Boot the current image from USB on the laptop, before it is wiped, and record how far it gets. FrancOS has no NVMe driver, so an NVMe laptop's internal drive is not touched. Secure Boot must be off; save the BitLocker recovery key first.
2. **Diagnostics.** Show loader and kernel progress on screen, keep errors visible, and record a boot log, because a laptop has no serial port.
3. **Firmware.** Use the real UEFI memory map, remove the fixed physical addresses, relocate or safely place the kernel, accept the panel's native resolution, and handle framebuffers above 4 GiB.
4. **Display.** Make the whole UI work at any resolution, including the IDE and Packages screens.
5. **Storage.** Add an NVMe driver and a filesystem that uses it, so the OS installs to the internal drive and persists there. The `FRANCFS1` limits are likely to need lifting here.
6. **Input.** Add xHCI and USB keyboard support, plus whatever the built-in keyboard needs. That could be PS/2-compatible, or I2C HID, which needs ACPI.
7. **Platform.** Add ACPI parsing, APIC timers and power-off. Consider multiple cores only if something requires them.
8. **Network.** Support a USB Ethernet adapter first. Built-in Wi-Fi is the weakest area: it usually needs a large driver and vendor firmware, so it stays out of scope unless the laptop's chip makes it practical.
9. **Installer.** Boot from USB, install to the internal drive, and boot without the stick. Secure Boot signing is a separate decision.

- **Tests:** every driver has QEMU tests in the laptop profile, including missing-device and failure cases. One acceptance journey runs in the emulator and on the laptop, using the same steps and expected results.
- **Done when:** the journey passes on the laptop from a cold boot off its internal drive, with any differences from the emulator listed and explained, and the QEMU matrix passes with no model-specific code outside the quirks table.
- **Limit:** only machines in the hardware support list count as tested. Being generalizable is not the same as broad verified support, and the project should claim only what has been tested.
- **Needs:** the laptop's make and model, because the keyboard, Wi-Fi and firmware details decide steps 6 and 8.

## Remaining dependencies after these phases

| Dependency | Used for | Path to removal |
|---|---|---|
| C: `boot/uefi/loader.c` | UEFI boot only | Rewrite in assembly |
| C: `frac.c`, `gfx.c` | Hosted interpreter | Retire once native covers its tests |
| Python: `franctxt/`, QEMU drivers, `tools/` | Host-side verification | Move to shell, then to in-guest checks |
| Python: `stage4/compiler.py` | Phase 0 check only | Replace with another independent path |
| GNU binutils | Build | Removed by Phase 3, except the first seed |

## Working rules

- One branch and PR per phase, with `main` protected by existing CI.
- After each phase run the full suite, including `stage4/qemu_home.py` and `stage4/uefi/test_boot.py`.
- Never move existing tags. New releases get new tags, only with owner approval.
- New tests use shell and data files, not Python.
